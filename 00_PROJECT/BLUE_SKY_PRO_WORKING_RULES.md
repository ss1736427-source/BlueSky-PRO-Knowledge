# BlueSky PRO — Правила работы

## 1. Режим работы

Основной режим проекта — непрерывное выполнение работы без лишних запросов пользователю.

Команды `go`, `делай`, `продолжай`, `проверяй` и аналогичные короткие команды означают: продолжить с текущего состояния проекта по утверждённому протоколу.

Если следующий технический шаг однозначен и не требует решения пользователя, исполнитель выполняет его сам.

## 2. Автоматическое продолжение

После завершения технического шага не требуется повторная команда пользователя, если следующий шаг определён и безопасен.

Если среда выполнения поддерживает автоматическое продолжение после остановки/завершения операции, следующий шаг инициируется через 5 секунд.

Пять секунд — это пауза между завершением одного технического шага и запуском следующего, а не причина запрашивать подтверждение пользователя.

## 3. Когда останавливаемся

Исполнитель останавливается только когда необходимо решение пользователя, которое нельзя надёжно вывести из уже утверждённых требований.

К таким случаям относятся:

- изменение архитектурного принципа;
- изменение утверждённого продуктового требования;
- изменение safety-ограничения;
- выбор между существенно различающимися вариантами поведения;
- нормативное или юридически значимое решение;
- неоднозначность, которую невозможно устранить проверкой имеющихся материалов.

Во всех остальных случаях исполнитель продолжает работу самостоятельно.

## 4. GitHub

Для работы с GitHub постоянно применяется `GITHUB_DEVELOPMENT_PROTOCOL.md`.

Перед существенным изменением проверяется актуальный `main` и связанные файлы. После изменения проверяются diff, тесты и CI именно для нового SHA.

Предыдущий успешный CI не считается подтверждением более нового commit.

## 5. Контекст проекта

При переходе между этапами сохраняются требования, принятые решения, незакрытые проверки, ограничения, текущая контрольная точка и последний подтверждённый SHA.

Нельзя повторно заставлять пользователя сообщать уже зафиксированные решения без объективной необходимости.

## 6. Минимализм изменений

Изменяется только необходимое для текущей задачи. Не допускаются ненужный рефакторинг, изменение уже утверждённого поведения или дублирование существующих решений.

## 7. Контроль качества

Технический шаг считается завершённым только после соответствующей проверки. Для критической логики используется цепочка:

```text
требование
→ реализация
→ тест
→ CI
→ контрольная точка
```

Неподтверждённое состояние явно обозначается как `UNVERIFIED`.

## 8. Постоянное соблюдение правил

Эти правила и `GITHUB_DEVELOPMENT_PROTOCOL.md` являются постоянной рабочей основой проекта.

Исполнитель должен обращаться к ним перед существенными изменениями и переходами между логическими блоками, даже если команда пользователя состоит только из `go`.

Если пользователь явно изменяет правило работы, последнее явное указание пользователя имеет приоритет, после чего соответствующий документ обновляется.
